S Situation

车险欺诈这个方向，做之前我没太关注过。但真正看进数据之后才发现，问题比想象的难——有些理赔单看每一条字段都是"正常"的，放在一起才能看出联合欺诈的痕迹。传统的人工加规则审核系统对这种情况基本没辙：规则太死板，人工审核一笔理赔要好几个小时，全靠审核员个人经验，无法规模化。做这个项目，不只是要训练个模型，而是要真正把流程跑通——从原始数据到最终的风控建议，中间每一步都要能说清楚。

T Task

我负责整个 Agent pipeline 的架构和编排。核心任务是把 fraud detection 从单模型实验变成一套完整工具——数据预处理、训练评估、选模、推理、决策输出这些环节都要跑通，而且最终输出得是人话，让不懂代码的审核员通过界面直接用，不需要每次都找工程师跑脚本。

A Action

我把整套流程拆成 6 个各司其职的 Agent，用一个共享的 AgentState 串联所有状态——从原始数据、清洗结果、训练模型、评估指标，到最终的欺诈概率、风险等级和置信度，全在这个共享状态里流转：

  • Preprocessing Agent — 清洗数据、编码类别变量，用 SMOTE 处理类别不平衡
  • Training Agent — 并行训练 Logistic Regression、Random Forest、XGBoost 三个候选模型
  • Evaluation Agent — 统一跑 accuracy、precision、recall、F1、AUC-ROC、confusion matrix
  • Model Selection Agent — 按业务阈值自动筛选，不是选 accuracy 最高的，而是选同时满足所有风控要求的那个
  • Inference Agent — 对新理赔样本输出欺诈概率
  • Decision Agent — 把数字翻译成风险等级、自然语言解释和可执行的处理建议

这是真正的 workflow orchestration——每个 Agent 有清晰的输入输出边界，选模逻辑是 business-driven 的，最后用 Gradio 把这一套变成非技术人员也能用的界面。

R Result

这套 pipeline 完整跑通了从理赔录入到风险报告的全流程。非技术用户可以在 Web 界面直接看到每条理赔的 Risk Level、欺诈概率、置信度、自然语言解释和推荐处理方式。

80.6% Recall
112 / 139 真实欺诈识别
6 Agents Pipeline 节点

最终自动选出 Logistic Regression——因为它是唯一一个同时满足所有业务门槛的模型，不是 accuracy 最高的那个。在 clear fraud、legitimate claim、ambiguous edge case 三类样本上，系统输出都符合预期。

S Situation

在 NUS 的一次 Fintech 课程项目里，我发现市面上的银行 App 对年轻人基本就是摆设——数据看不懂，理财建议是"建议减少非必要支出"这种废话，Gen Z 压根不会在意。新加坡的年轻用户其实很多人有投资意识，但银行给他们的工具完全跟不上。我当时就想：如果让我来做，会是什么样的？

T Task

我要独立设计并实现一个真正面向 Gen Z 的银行仪表盘——不只是展示数据，而是要能帮用户搞清楚"我的财务状况到底怎么样"、"我的钱应该放在哪"。限制是没有后端、没有真实 API，所有功能必须用纯前端实现，包括图表渲染、评分引擎和个性化建议。

A Action

我设计了六个模块，各自独立但数据全部联动：总览、财务健康、AI 理财建议、FHI 评分引擎、储蓄目标、投资组合。

  • FHI 评分引擎是我自己设计的评估模型，把消费结构、储蓄率、投资比例等维度加权合成一个 0–100 的动态分数，实时反映用户的财务健康状况，而不是一个静态标签
  • 图表渲染用 Canvas 手写实现，没用任何第三方图表库，支持实时动态更新
  • AI 理财建议模块基于用户当前数据在前端生成针对性文字建议，不是模板套话
  • 所有模块数据联动——用户改一个输入，整个仪表盘立刻响应，体验比大部分银行 App 流畅
R Result

做出来的东西感觉已经不太像课程作业了，更接近一个可以直接给用户用的产品原型。演示的时候导师点评说是课程里少数几个"真的有 product sense"的作品，没有只是堆功能，而是站在用户角度设计了完整的信息架构。

S Situation

工业设备故障预测不是什么新鲜话题，很多工厂早就有 ML 模型在跑，但真正被维护团队用起来的很少。最大的问题不是模型不准，而是工程师不信任它——它给一个风险分数，你不知道它为什么这么说，也不知道应该先去处理哪台机器。黑箱是落地最大的拦路虎，不是准确率。

T Task

我要做的不只是训练一个准确的故障预测模型，而是让它的输出变成维护团队能看懂、能直接执行的信息。目标是把 AI 告警从"黑箱警报"变成"有理由的建议"，让工具真正被用起来。

A Action

先训练 Random Forest 做设备故障分类，然后叠了四种 XAI 方法，从不同角度把预测结果解释清楚：

  • SHAP — 全局层面，看哪些特征对模型预测影响最大，给维护团队一个"这套系统在关注什么"的整体认知
  • LIME — 单条样本层面，针对每台机器说清楚"它为什么被标记为高风险"，每条告警都有具体理由
  • Permutation Importance — 验证特征的稳定性，防止模型依赖了噪声特征
  • Partial Dependence Plot — 展示关键特征和故障概率的关系曲线，帮工程师知道阈值在哪里、往哪个方向变化会触发风险

最后把这些输出整合成一个 Triage 视图：每条告警除了风险分数，还有"主要触发因素"排序和"建议优先处理顺序"，维护人员看完就知道今天该先去哪里。

R Result

模型在测试集上 AUC 达到 0.95，准确率 91%。但我觉得这个项目真正有意思的地方是它验证了一件事：模型解释不是锦上添花，是 AI 工具能真正落地的前提条件。

最终交付的是一个 human-in-the-loop 工业 Triage 工具：高/中/低三级优先级，每条告警附带自然语言成因说明，维护团队可以直接按这个顺序安排当天的检修计划，不需要再去翻数据自己判断。

S Situation

200 万+ 条贷款记录，数据脏、字段缺失、标签还有冲突——这是这个项目给我的第一个下马威。更麻烦的是，业务本身也在一个扩张过快、风险已经在往上走的阶段，但当时的分析体系还停留在"事后描述"的层面，根本说不清楚问题出在哪、该怎么改。

T Task

我需要从头搭一套完整的分析和决策支持体系。不只是说清楚"现在情况怎样"，而是要能告诉业务："风险为什么上升"、"组合该怎么调整"、"哪些用户值得花成本留、哪些补贴基本是白给"。

A Action

我分五个模块推进，每个对应一个具体的业务问题：

  • 数据治理与指标体系 — 清洗标准化核心字段，识别结构性缺失，从零构建 ECL、违约率、CLV、流失概率等指标
  • 增长-风险关系分析 — 找出"早期激进扩张拉高了资产质量风险"这个核心问题，用成熟期偏差（maturity bias）修正了一开始容易误判的地方
  • 信用风险建模 — 对比 Logistic Regression 和 Random Forest，调优分类阈值，把坏客户识别能力推到 AUC 0.75
  • 资产组合优化 — 在 50% 流动性冲击的约束下，按风险调整收益筛选组合，同时设 PD cap 把尾部风险控住
  • 用户留存策略 — 结合 Churn 模型（AUC 0.90+）和 CLV 分层，弄清楚哪些用户值得花成本留、哪些补贴基本是在浪费预算
R Result

把分析从"描述现状"升级成了"给出策略"——descriptive 到 predictive 到 prescriptive，完整链路跑通了。

最终交付覆盖了增长策略、风险定价、市场定位（重点挖掘 near-prime 客群）、数据治理路径和 AI 落地方向。做完这个项目我才真正意识到：数据分析的终点不是报告，是决策。

S Situation

NUS 强化学习课的大作业，要求在 MiniGrid 多个环境上跑 agent。大部分同学的思路很直接：挑一个算法，把所有场景都跑一遍，调调参看效果。但我在看任务设计的时候注意到一个细节：Empty Navigation、DoorKey、FourRooms 这几个环境的结构差别其实很大——有的需要从观察里学策略，有的环境本身就是可以直接规划的。强行用同一套方法解决所有场景，感觉是在回避真正有意思的问题。

T Task

我想验证一个判断：不同结构的环境，该用不同的决策范式。与其在一个框架里死磕，不如系统比较学习驱动（DQN）和规划驱动（BFS）各自的适用边界——能不能拿数据把这个说清楚。

A Action

我把实验拆成两条线，分别针对不同的任务特性：

  • DQN + MLP — 用在 Empty 等观察驱动的导航任务，让 agent 从像素级观察里学策略，适合状态空间大、结构不固定的场景
  • BFS 规划 — 用在 DoorKey、FourRooms 等有固定空间结构的任务，直接利用环境的可观测性搜最优路径，不需要"学"，直接"算"

两条线用同一套指标（任务成功率、收敛步数、泛化稳定性）横向对比，目标不是把各自调到最优，而是真正说清楚"哪种方法在哪种环境下有优势，为什么"。

R Result

结论很清楚：BFS 在结构化场景里把 DQN 碾压——收敛速度快 10 倍以上，成功率接近 100%，DQN 在同样任务上频繁卡在局部最优。但 DQN 在状态空间更复杂、结构不固定的场景里韧性明显更好。
